## 1. 开发背景

### 1.1 用户痛点

用户到景点旅游时，想知道眼前这处景点的历史故事。虽然网上能查到，但存在三个问题：

1. **要主动搜、要自己找**：得先知道这是什么，再去搜，流程断裂，游玩节奏被打断。
2. **缺少"导游感"**：网上是冷冰冰的文字资料，不是有温度的讲述，没有"有个人在旁边给我讲"的陪伴感。
3. **定制感缺失**：跟团导游要照顾一群人，讲得泛、讲得赶；用户想要的是"只对我一个人讲"。

### 1.2 需求本质

> **把"搜索 + 阅读"变成"拍照 + 倾听"，把公共导游变成私人导游。**

核心体验关键词：**边走边听、即时、沉浸、可信、私密**。

### 1.3 为什么现有产品没解决

市面产品（高德/百度语音导览、三毛游、美景听听等）普遍是**列表式点播**：用户自己在列表里找景点、手动点播放。问题在于：

- 冷启动覆盖差：没被收录的小景点、冷门建筑，一律没内容。
- 交互断裂：要"找—点—播"，不是"到了—就听"。
- 内容不可溯源：讲得对不对，用户无从判断。

本项目用「**拍照识别 + AI 实时生成 + 来源可溯**」绕过以上三个问题：不依赖预置内容库（覆盖无限），交互是"举起手机就有"（无断裂），每段讲解带来源（可信）。

## 2. 产品定义与目标

### 2.1 一句话定义

一个"边走边听"的私人 AI 导游：用户到景点后**拍一张照片**，App 识别出这是哪里，**经用户确认**后，用像导游一样的语气讲出这里的历史故事，且**每段讲解都可溯源、确保真实性**。

### 2.2 核心闭环

```
打开 App
   ↓
[首页] 大而美的拍照按钮（唯一主入口，无列表无地图）
   ↓
拍照 / 从相册选择
   ↓
[识别中] 视觉模型识别（约 1-3 秒）
   ↓
[确认弹层] "我认出来这是「太和殿」，对吗？"
   ├─ 对   → 进入讲解
   └─ 不对 → 用户手动输入文字描述 → 重新识别 → 进入讲解
   ↓
[讲解页] 语音播报 + 文字同步高亮 + 来源标注
   ├─ 播放 / 暂停 / 进度
   ├─ 继续探索：推荐附近可讲点位
   └─ 再拍一张：直接进入下一次识别
```

### 2.3 目标用户与非目标

| 项 | 内容 |
|---|---|
| **目标用户** | 自由行游客、文化历史爱好者、独自或小团体出行者 |
| **典型场景** | 到达景点，站在建筑物前，想立刻知道这是什么、有什么故事 |
| **非目标（本期不做）** | 团队游管理、门票预订、酒店/餐饮推荐、社交分享、离线地图导航 |

### 2.4 产品成功的判断标准

1. 用户在景区里，**从举起手机到听到讲解 ≤ 5 秒**（含识别+确认）。
2. 讲解内容**可被来源验证**，不是 AI 自说自话。
3. 用户**愿意连续拍 5 处以上**（说明体验流畅、有引导感，不是一次性玩具）。

## 3. 开发方式与技术路线

### 3.1 两阶段交付（用户明确定调）

```
┌─────────────────────────────────────────────────────┐
│  阶段一：Web H5 原型（当前目标）                       │
│  ├─ 响应式 H5，手机浏览器打开即可用                     │
│  ├─ 完整交互闭环：拍照 → 识别 → 确认 → 讲解             │
│  ├─ 真实 API 接入，可直接带去景区实测                   │
│  ├─ 真实视觉稿（不是线框图）                            │
│  └─ 目标：定死交互流程和视觉样式                         │
└─────────────────────────────────────────────────────┘
                        ↓ 用户确认界面后
┌─────────────────────────────────────────────────────┐
│  阶段二：打包为 App                                   │
│  ├─ 方案 A：Capacitor / Tauri 套壳（改动最小，复用代码）│
│  ├─ 方案 B：Flutter 重写 UI（体验最好，成本最高）        │
│  └─ 关键升级：原生后台播放 TTS（Web 做不到）            │
└─────────────────────────────────────────────────────┘
```

**为什么先做 Web**：
- 反馈最快：改完刷新就能看，不用打包、不用装机、不用上架。
- 验证成本最低：用户能直接在手机上打开试用，确认交互和视觉。
- 代码可复用：套壳方案下，H5 代码可 80% 以上复用到 App。

### 3.2 技术栈选型

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | **原生 HTML + CSS + 原生 JS**（无框架） | 单页原型，无需构建工具；避免引入 Vue/React 的构建复杂度；便于逐屏截图核对 |
| 样式 | 手写 CSS（CSS 变量管理主题色） | 精细控制视觉，符合"美观优先"要求 |
| 本地中转服务 | **Node.js（Express）** 或 Python（FastAPI） | 隐藏 API 密钥、代理第三方调用、解决浏览器 CORS |
| 相机 | `navigator.mediaDevices.getUserMedia` + `<input type="file" accept="image/*" capture>` | 前者做取景框，后者做相册导入兜底 |
| 定位 | `navigator.geolocation` | 用于"附近点位"推荐（非主流程） |
| 语音 | `window.speechSynthesis`（Web Speech API） | 原型阶段零成本出声 |
| 存储 | `localStorage` / `IndexedDB` | 存历史记录、缓存讲解结果 |

**明确不用框架的原因**：这是**交互原型**，不是生产级应用。无框架 = 无构建步骤 = 改一行立刻见效 = 文件可直接丢给用户本地打开。等进入 App 阶段再决定是否重构。

### 3.3 密钥安全策略（重要）

```
❌ 错误做法：前端 JS 里直接写 API Key → 任何人打开 F12 就能看到
✅ 正确做法：前端只调用本地服务 → 本地服务持有 Key 再调 TaoToken
```

- 密钥只存在**本地服务端配置文件**（如 `server/.env`，加 `.gitignore`）。
- 前端代码中**不得出现任何形如 `sk-xxx` 的字符串**。
- 打包 App 阶段：密钥要么放自有服务端，要么改走账号体系代理调用。

## 4. 功能说明（完整）

### 4.1 功能清单总览

| 编号 | 功能 | 优先级 | 阶段 |
|---|---|---|---|
| F1 | 拍照识别入口 | P0 | 阶段一 |
| F2 | 相册导入识别 | P0 | 阶段一 |
| F3 | 识别结果确认/修正 | P0 | 阶段一 |
| F4 | AI 生成讲解（含溯源） | P0 | 阶段一 |
| F5 | 语音播报 + 文字同步高亮 | P0 | 阶段一 |
| F6 | 来源标注展示 | P0 | 阶段一 |
| F7 | 附近可讲点位推荐 | P1 | 阶段一 |
| F8 | 讲解历史记录 | P2 | 阶段一（可选） |
| F9 | 音色/长度设置 | P2 | 阶段一（可选） |
| F10 | 原生后台播放 | P0 | 阶段二 |
| F11 | 大厂 TTS 音色 | P1 | 阶段二 |

### 4.2 F1 — 拍照识别入口

**描述**：首页是唯一主入口，一个大而美的拍照按钮。

**行为**：
1. 点击拍照按钮 → 唤起相机取景框（或系统相机）。
2. 拍摄后 → 上传至后端 → 进入识别流程。
3. 支持"从相册选择"作为**同等重要的第二入口**（站人堆里举手机尴尬时用）。

**设计要求**：
- 不能是廉价的"一个圆形按钮"。建议做**取景框形态**（四角有边框标记），传递"对齐拍摄"的暗示。
- 背景用当季风景的**渐变 + 模糊摄影图**，营造氛围。
- 底部放**示例引导卡**（"试试对着太和殿 / 兵马俑拍照"），降低"不知道能拍什么"的困惑。

**边界情况**：
- 用户拒绝相机权限 → 引导使用相册导入。
- 拍照过于模糊 → 提示"试着把建筑拍得更完整、更清晰"。

### 4.3 F2 — 相册导入识别

**描述**：允许从相册选图，用途有两个：事后补讲解、避开当众拍照的尴尬。

**行为**：`<input type="file" accept="image/*">` → 拿到 File → 压缩（可选）→ 上传识别。

**注意**：Web 端需要注意大图上传耗时，建议**前端压缩到长边 1280px、JPEG 质量 0.8** 再上传。

### 4.4 F3 — 识别结果确认/修正

**描述**：识别后**不直接开始讲解**，先弹确认层让用户核对。这是保证准确性的关键设计。

**界面文案**：
```
我认出来这是「太和殿」
                    [ 对，就是它 ]  [ 不对，我来说 ]
```

**行为分支**：
| 用户操作 | 后续 |
|---|---|
| 点"对" | 用识别出的点位名进入讲解生成 |
| 点"不对" | 展开输入框："用一句话描述这是什么？（例如：乾清宫前的铜龟）" → 提交 → **用用户描述重新识别/直接生成** |
| 关闭弹层 | 返回首页 |

**为什么必须保留这一步**：视觉模型对建筑细分（太和殿 vs 保和殿）可能不准，讲错故事比不讲更糟。让用户一秒钟确认，成本极低、收益极高。

**识别失败的处理**：如果模型返回"无法识别"或置信度低，直接跳到**输入框态**，提示"没能认出来，你可以描述一下这是什么吗？"

### 4.5 F4 — AI 生成讲解（含溯源）

**描述**：核心功能。基于确认后的点位，生成 2-3 分钟、500-800 字、混合风格的讲解词。

**内容规格**：

| 项 | 规格 |
|---|---|
| 长度 | 500-800 字（约 2-3 分钟口播） |
| 结构 | ① 说书人式开场（一句话钩子） ② 历史脉络（知识型，严谨） ③ 关键故事 ④ 一个细节彩蛋 |
| 风格 | **知识型骨架 + 说书人式提味**：事实陈述严谨，开场和彩蛋生动 |
| 真实性 | 只基于给定资料作答；资料未提及的不许编；有争议时写"另有一说……" |
| 来源 | 输出中带 `sources` 字段，UI 显示为正文下一行小字 |

**生成输入要素**：
1. 点位名称（识别结果或用户描述）
2. **联网检索到的真实资料**（维基百科/官方介绍等公开权威源）
3. 生成约束提示词（见 5.2）

### 4.6 F5 — 语音播报 + 文字同步高亮

**描述**：讲解以语音为主、文字为辅，两者同步。

**行为**：
1. 进入讲解页 → **自动开始播报**（用户可立即暂停）。
2. 讲解文本按句分段，**当前播报的句子高亮**。
3. 播放控制：播放 / 暂停 / 进度条 / 拖动跳转。
4. 用户点击任意句子 → 从该句开始播报。

**技术要点**：
- Web Speech API 的 `onboundary` 事件可获知朗读进度，用于驱动高亮——**但各浏览器支持度不一**，需做降级：不支持时按句子均分时长估算高亮。
- **必须做文本预处理**：把"太和殿"、"明永乐十八年"等替换/注音，避免 TTS 读错（可用同音字替换，如"和"→"hé"场景判断；或直接接受 Web TTS 的局限，App 阶段用大厂 TTS 解决）。

### 4.7 F6 — 来源标注展示

**描述**：用户选择了**轻标注**方案——简洁不打断听感。

**UI 呈现**：
```
（讲解正文……）

资料来源：故宫博物院官网、维基百科「太和殿」条目
```

- 位置：讲解正文**最下方**，字号小、颜色浅（次要视觉层级）。
- 可点击：点开展示来源列表（标题 + 链接），用户可自行核验。
- 如果来源有冲突：正文内嵌一句"另有一说……"，不在来源区展开。

**为什么选轻标注**：逐句溯源交互复杂、打断沉浸感；轻标注在"看起来干净"和"有据可查"之间取得平衡。底层生成约束**不因此放松**。

### 4.8 F7 — 附近可讲点位推荐

**描述**：讲完一处后，底部给"继续探索"引导，形成"导游带着走"的连贯感。

**呈现形式**：
```
继续探索
─────────────
📍 中和殿        距你约 30 米
   明清皇帝上朝前休息的地方

📍 保和殿        距你约 80 米
   科举殿试的考场

[ 再拍一张 ]
```

**实现思路**：
- 优先用**定位 + 已识别点位的地理关联**推荐。但点位地理数据冷启动困难。
- **降级方案（原型阶段采用）**：让 AI 在生成讲解时，顺带输出 2-3 个"同一景区的相邻点位"名称及一句话简介，用文字而非真实距离呈现（避免假数据）。
- 用户点击推荐项 → 直接以该点位名进入讲解生成（**无需再拍照**），提升连贯性。

### 4.9 F8 — 讲解历史记录（P2，可选）

**描述**：记录用户拍过/听过的点位，形成"我的足迹"。

- 存 `localStorage`：`{ 点位名, 图片缩略图, 讲解文本, 时间戳 }`
- 用途：可重听、可回看、可形成旅行日志感。

### 4.10 F9 — 音色/长度设置（P2，可选）

- **音色试听**：让用户在原型阶段就感受音色差异（Web Speech API 提供系统音色列表，可枚举选择）。
- **长度档位**：快讲 / 标准 / 深讲（默认标准）。用户选了 B 标准版，但保留扩展位。

### 4.11 F10 / F11 — App 阶段功能

| 功能 | 说明 |
|---|---|
| 原生后台播放 | 锁屏、切后台继续播报。Web 做不到，必须原生（阶段二核心升级点） |
| 大厂 TTS 音色 | 接入火山/讯飞/Azure，音色自然度远超 Web Speech API |
| 系统级分享 | 分享讲解内容/旅行足迹 |

## 5. 实现思路（核心算法与流水线）

### 5.1 总流水线

```
用户拍照
   │
   ▼
[1] 图片预处理（前端）：压缩到长边1280px / JPEG 0.8
   │
   ▼
[2] 上传到本地中转服务 /api/recognize
   │
   ▼
[3] 视觉识别：调 glm-5.3-flash（image_url）
   │   Prompt: "识别图中的中国景区建筑/文物，返回{name, confidence, location_hint}"
   │   输出：JSON
   ▼
[4] 用户确认/修正 → 得到最终 pointName
   │
   ▼
[5] 资料检索 /api/research
   │   调公开资料源（维基百科 API / 搜索），拉取真实资料文本
   │   输出：raw_materials[]
   ▼
[6] 讲解生成 /api/guide
   │   调 deepseek-v4-pro，输入「点位名 + raw_materials + 生成约束」
   │   输出：{title, script, sections[], sources[], nearby[]}
   ▼
[7] 前端渲染 + TTS 播报 + 文字高亮
   │
   ▼
[8] 附近点位推荐 → 用户点选 → 回到 [5]（跳过拍照）
```

### 5.2 关键 Prompt 设计

**识别 Prompt（视觉模型）**：
```
你是景区建筑识别专家。请识别图片中的主要建筑或文物。
只返回 JSON，不要任何额外解释：
{
  "name": "识别到的名称（如'太和殿'）",
  "confidence": 0.0-1.0,
  "location_hint": "可能所在景区（如'北京故宫'）",
  "recognized": true/false,
  "reason": "判断依据（简短）"
}
如果无法识别或不确定，recognized 设为 false。
```

**生成 Prompt（文本模型，核心）**：
```
你是一位资深私人导游。请基于【参考资料】为用户讲解【点位名称】。

【参考资料】
{raw_materials}

【硬性约束】
1. 只能使用参考资料中的信息，资料未提及的内容绝对不许编造。
2. 如果资料对某个事实有争议，用"另有一说……"一句带过，不展开。
3. 如果参考资料不足以支撑讲解，直接说明"目前缺乏可靠资料"，不要硬凑。

【风格要求】
- 长度 500-800 字，口播约 2-3 分钟。
- 开场用一句有悬念/画面感的话抓住注意力（说书人式）。
- 主体按时间脉络讲清"是什么、为什么重要"（知识型，严谨）。
- 结尾留一个细节彩蛋（有意思的小知识点）。
- 语言口语化，适合朗读，避免书面语长句。

【输出格式】只返回 JSON：
{
  "title": "讲解标题",
  "script": "完整讲解词（用于 TTS 播报，纯文本无 Markdown）",
  "sections": [{"text": "分段文本", "type": "hook|history|story|trivia"}],
  "sources": [{"name": "来源名称", "url": "来源链接"}],
  "nearby": [{"name": "相邻点位名", "intro": "一句话简介"}]
}
```

### 5.3 真实性保障三层机制

```
┌──────────────────────────────────────────────────┐
│ 第一层：生成时约束                                 │
│ 只喂可信资料，要求 AI 只基于给定资料作答。          │
│ 资料没写的 → 明说不知道，而非编造。                 │
├──────────────────────────────────────────────────┤
│ 第二层：溯源托底（关键）                            │
│ 讲解所需资料【实时联网拉取真实公开网页】。          │
│ 真实性不靠 AI 自觉，而是每段讲解都有真实资料托底。  │
├──────────────────────────────────────────────────┤
│ 第三层：冲突降级                                   │
│ 年代/人物/事件有争议 → 正文一句"另有一说……"。      │
│ 不展开、不单列可信度标签（因用户选择轻标注）。      │
└──────────────────────────────────────────────────┘
```

**为什么第二层是关键**：单纯让 AI "讲得准"是不可靠的（幻觉无法根除）。但**先检索真实资料、再让 AI 基于资料改写**，幻觉空间被压缩到"资料本身"这个边界内。这是本项目"真实性"卖点的技术根基。

### 5.4 资料检索实现思路

**原型阶段（低成本可用）**：
- 维基百科 API：`https://zh.wikipedia.org/api/rest_v1/page/summary/{点位名}` → 拿摘要
- 中文维基搜索：`https://zh.wikipedia.org/w/api.php?action=query&list=search&srsearch={关键词}`
- 可补充：Bing/Google 搜索 API（需另配密钥，可选）

**注意事项**：
- 维基/百科质量参差，权威性有限，但**可溯源**（能看到链接），比纯 AI 生成强。
- 权威源（地方志、文保单位资料）常无公开 API → 原型阶段先用公开网页源，后续可人工补充权威资料库。

### 5.5 TTS 与文字同步实现思路

```
方案：先整段取出 script → 按标点切分成句子数组 → 
     逐句调用 speechSynthesis.speak(utterance) → 
     当前句索引变化时更新高亮样式
```

**关键点**：
- 逐句 speak 比整段 speak 更易控制高亮，也便于"点击某句从该句开始"。
- 需处理浏览器"用户未交互不允许自动播放"的限制 → **首次必须由用户点击触发**（可在确认层点"对"时即算用户交互）。
- `speechSynthesis` 需在页面卸载时 `cancel()`，避免残留播放。

### 5.6 附近点位推荐实现思路

**原型阶段（无地理数据）**：
- 由生成模型在 `nearby` 字段输出相邻点位（模型知识中通常有"故宫前朝三大殿"这类关联）。
- UI 显示为"继续探索"卡片，**不显示真实距离**（避免编造），或显示"同区域"。

**进阶阶段（有地理数据后）**：
- 建立 `景点点位坐标表`：`{name, lat, lng,景区名, 简介}`
- 用户当前定位 → 计算 haversine 距离 → 取最近 3 个 → 显示真实距离。
- 数据来源：OSM（OpenStreetMap）可查部分景点坐标；或人工维护。

## 7. API 接入规范（换模型必读）

### 7.1 服务商与入口（已实测）

| 项 | 值 |
|---|---|
| 服务商 | TaoToken 中转 |
| Base URL（**有效**） | `https://api.taotoken.net/v1` （按量付费） |
| 协议 | OpenAI 兼容（Chat Completions） |
| 完整地址 | `https://api.taotoken.net/v1/chat/completions` |
| 鉴权 | `Authorization: Bearer <API_KEY>` |
| ❌ 不可用入口 | `https://api.taotoken.net/token/v1` → 返回 `insufficient_quota` |

**实测记录（2026-10-09）**：
```
POST https://api.taotoken.net/v1/chat/completions
body: {"model":"glm-5.3-flash","messages":[{"role":"user","content":"..."}],"max_tokens":10}
→ 200 OK，正常返回 choices[0].message.content
```

### 7.2 模型清单与选用

| 用途 | 主选 | 备选 | 关键能力要求 |
|---|---|---|---|
| **拍照识别** | `glm-5.3-flash` | `Kimi-K3`、`qwen3.8-27b`、`deepseek-v4-flash-vision-exp` | 必须 `supported_modalities` 含 `image_url` |
| **讲解生成** | `deepseek-v4-pro` | `qwen3.7-max`、`glm-5.3` | 长文本生成、指令遵循强 |

**其他可用模型**（供替换参考）：`glm-5.3`、`glm-5.2`、`glm-5.1`、`Kimi-K2.6`、`deepseek-v4-flash`、`qwen3.7-max`、`qwen3.8-27b`

### 7.3 换模型时只需改哪里

设计上**模型名集中配置**，换模型不需要动业务逻辑：

```
server/.env
─────────────────────────────
TAOTOKEN_API_KEY=sk-xxxx
TAOTOKEN_BASE_URL=https://api.taotoken.net/v1
MODEL_VISION=glm-5.3-flash          ← 换识别模型改这里
MODEL_TEXT=deepseek-v4-pro          ← 换生成模型改这里
```

**换模型检查清单**：
1. 该模型是否支持所需模态？（识别必须支持 `image_url`）
2. 该模型的 `contextLen` 是否够放下资料 + 输出？
3. 返回格式是否兼容？（本方案要求返回 JSON，若模型 JSON 能力弱，需加 `response_format` 或容错解析）
4. 计费入口是否正确？（务必用 `/v1` 按量付费入口）
5. 改完跑一遍 `/api/recognize` 和 `/api/guide` 自测。

### 7.4 图片输入格式（OpenAI 兼容）

```json
{
  "model": "glm-5.3-flash",
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text", "text": "识别图中建筑，返回 JSON"},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}
    ]
  }]
}
```

## 8. UI/UX 设计规范

### 8.1 设计原则

| 原则 | 说明 |
|---|---|
| **氛围优先** | 不做"工具感"界面，要有文化/旅行的质感 |
| **单入口** | 首页只突出一个动作：拍照。不堆功能 |
| **减少往返** | 讲解页底部直接给"继续探索"，避免回首页 |
| **不假设** | 识别不准时明确让用户修正，不装作很懂 |

### 8.2 视觉基调建议

- **主色**：建议中国风低饱和色系（如黛青 `#2F4F4F`、朱砂 `#9E3D3D`、宣纸米 `#F5F1E8`），呼应历史文化主题。
- **字体**：标题可用衬线（宋体/思源宋体）增文化感，正文用无衬线保证可读性。
- **背景**：首页用当季风景图的**高斯模糊 + 渐变遮罩**，突出按钮。
- **动效**：识别中给骨架屏/脉冲动画；讲到新句时文字高亮平滑过渡。

### 8.3 页面清单（约 4-5 屏）

| 页面 | 内容 |
|---|---|
| 1. 首页 | 取景框形态拍照按钮 + 氛围背景 + 底部示例引导卡 + 相册导入入口 |
| 2. 识别确认层 | 弹层："我认出来这是「太和殿」，对吗？" + 确认/修正 + 手动输入框 |
| 3. 讲解页 | 语音播放器（播放/暂停/进度）+ 文字同步高亮 + 来源小字 + "继续探索"推荐 + "再拍一张" |
| 4. 探索/历史页（可选） | 拍过的点位记录、听过的讲解 |
| 5. 设置页（可选） | 音色试听、长度档位 |

### 8.4 用户体验细节（必须处理）

| 问题 | 解决方案 |
|---|---|
| 首页只有一个按钮，显廉价 | 按钮做成取景框形态；背景用风景模糊图 |
| 当众举手机拍照尴尬 | **相册导入**作为同等入口 |
| 拍歪/拍到路人 | 识别失败时提示"试着把建筑拍完整" |
| 不知道能识别什么 | 首页底部示例引导卡 |
| 讲完不知道去哪 | "继续探索"推荐附近点位 |
| 不知道讲到哪 | 文字同步高亮 + 进度条 |
| 想跳过某段 | 点击任意句子从该句播报 |

## 10. 需求决策记录（含取舍理由）

| # | 维度 | 决策 | 为什么这么选 | 放弃了什么 |
|---|---|---|---|---|
| 1 | 内容来源 | AI 实时生成 | 不依赖预置内容库，任何景点都能用，冷启动零成本 | 初期内容质量不如精编内容库 |
| 2 | 真实性 | 轻标注 | 简洁不打断听感，同时保证可溯源 | 放弃了逐句溯源的强追溯性 |
| 3 | 粒度 | 点位级 | 最接近"导游指着讲"的体验 | 需要 AI 具备建筑级识别能力 |
| 4 | 主入口 | 拍照 | 绕过 GPS 精度问题，仪式感强 | 需处理识别准确率问题 |
| 5 | 交互 | 识别+确认 | 用极低成本规避"讲错故事"的致命体验 | 多了一次点击 |
| 6 | 兜底 | 手动输入描述 | 覆盖 AI 完全不认识的冷门对象 | 依赖用户描述质量 |
| 7 | 引导 | 附近点位推荐 | 形成"导游带着走"的连贯感 | 需额外生成相邻点位数据 |
| 8 | 长度 | 标准版 2-3 分钟 | 平衡信息量与会话时长 | 重头景点可能不够深 |
| 9 | 风格 | 混合（知识骨架+说书提味） | 兼顾真实与有趣 | 需要更精细的 Prompt 控制 |
| 10 | 语音 | 先系统 TTS 后大厂 | 原型不被密钥/成本卡住 | 原型音色较机械 |
| 11 | API | 全真实接入 | 原型即可带去景区实测 | 产生实际调用费用 |
| 12 | 形态 | 先 Web 后 App | 反馈最快、成本最低 | Web 无法后台播放 |

## 12. 风险清单与应对

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 视觉模型认不准建筑细分 | 讲错对象 | ①"用户确认"步骤兜底 ②识别 Prompt 要求输出 confidence ③低置信度直接转手动输入 |
| R2 | 来源资料质量参差 | 追溯性存疑 | 原型先接受；后续建权威资料库（地方志等） |
| R3 | Web 锁屏停止播报 | 边走边听中断 | 原型阶段明确告知；App 阶段原生解决 |
| R4 | 识别+生成延迟（3-15s） | 破坏沉浸感 | ①加载动画 + 分步反馈 ②后续做"进景区预生成缓存" |
| R5 | AI 幻觉 | 讲错历史 | 三层机制（约束+溯源+降级） |
| R6 | API 密钥泄露 | 被盗刷 | 密钥只存服务端；代码不出现 sk- 字样；定期更换 |
| R7 | 按量付费成本 | 费用不可控 | 加调用日志与费用统计；测试时限制调用频次 |
| R8 | 浏览器 TTS 兼容差异 | 部分机型无声 | 检测 `speechSynthesis` 支持；不支持则降级为纯文字 |
| R9 | JSON 解析失败 | 流程中断 | 生成时用 `response_format: json_object`（若支持）+ 容错解析（剥离 markdown 代码块） |

## 13. 验收标准

### 13.1 功能验收（阶段一）

| 术语 | 含义 |
|---|---|

### 15.1 语音双 provider 架构（v1.2）

```
speech.js（前端，接口不变）
├── provider = 'edge'   默认。逐句 POST /api/tts → MP3 → <audio> 顺序播放
│                        音色：晓晓/云希/云健 等 8 个中文神经音色，localStorage 记忆
│                        合成结果按句缓存（objectURL），重听不二次请求
│                        失败自动跳句，不卡死整篇
└── provider = 'system' 离线兜底。Web Speech API，逻辑与 v1.1 相同

server/services/tts.js   msedge-tts 库封装
├── synthesize(text, voice, {rate,pitch,volume}) → MP3 Buffer
│    默认韵律 rate=-4% pitch=+2Hz（娓娓道来不机械）；超长文本按标点切段
├── listVoices() → 8 个精选中文音色（带缓存）
└── 免费原理：复用 Edge 浏览器"大声朗读"通道，无需任何密钥
```

### 15.2 ⚠️ 打包 APP 时语音模块必读（TODO 清单）

**Web 端 Edge TTS 方案在 App 里不可直接沿用**，打包时必须处理以下事项：

1. **CORS/网络层**：App WebView 里 `fetch('/api/tts')` 同源假设失效，需改为完整地址或内置本地服务
2. **后台播放（P0）**：WebView 切后台 `<audio>` 会被暂停，必须接原生播放器插件（如 Capacitor 的 NativeAudio）或改云 TTS + 原生后台任务
3. **音质升级（原规划 F11）**：App 阶段建议正式接入云 TTS（阿里百炼 CosyVoice / 火山豆包，均有免费额度）——`speech.js` 已预留 provider 扩展点，新增一个 provider 即可，前端 UI 不用动
4. **Edge TTS 合规风险**：该通道是浏览器"大声朗读"接口的复用，微软未提供商用授权，App 上架后流量特征明显、存在被封锁风险——**App 正式版务必切换云 TTS**
5. **离线兜底**：`system` provider 依赖系统 TTS 引擎，Android 需确认设备装有 Google TTS 或国产厂商语音引擎，iOS 自带可用

### 15.3 配置中心与后端地址解析（v1.3）

**目标：换密钥 / 换模型 / 换服务商零改码、零重打包；App 阶段换密钥与 Web 完全同构。**

```
服务端（密钥的家，永不外泄明文）
server/config.js 三级优先级：内置默认 → server/.env → server/data/config.json（热切换层）
├── update(patch)   白名单字段写入 runtime，apiKey 空值=不修改
├── snapshot()      脱敏快照（keyMask 掩码），可安全下发前端
├── selfTest()      GET {baseUrl}/models 验证连通性/视觉模型
└── refresh()       热生效，client.js 引用同一 CONFIG 对象

server/index.js 新增路由
├── GET  /api/endpoint     地址发现（App 填地址后的验证端点，回显 baseUrl/provider/模型）
├── GET  /api/config       读配置（脱敏）
├── POST /api/config       写配置（可选 CONFIG_TOKEN 口令保护），热生效
└── POST /api/config/test  连通性自检
（另有 CORS 中间件：App WebView 跨域必需，ALLOW_ORIGIN 可收紧）

前端（只管"连哪个后端"，永不知道密钥）
web/env.js              打包时写入默认 BASE_URL（可为空）
web/scripts/config.js   地址解析：localStorage 用户填写 > env.js 内置 > 同源相对路径
                        probe()/testAndSave() 用 /api/endpoint 验证后再保存
web/scripts/api.js      BASE 改为函数取值，每次请求现取（改地址立即生效）
web/scripts/speech.js   TTS 请求同样走 AppConfig.base()
web/index.html          首页齿轮 → "服务设置"弹层：连接状态卡 / 地址测试与保存 /
                        服务端配置只读展示 / 高级面板（改密钥·服务商·模型，含口令位）
```

**App 阶段三种部署架构**（密钥永不进 App 包）与打包 Checklist 见根目录《API密钥与配置更换指南.md》。

## 16. 快速上手（给接手者的三句话）

1. **要改模型 / 换密钥**：网页右上角齿轮 → 服务设置 → 高级面板直接改（热生效）；或改 `server/.env` 重启。识别模型必须支持 `image_url`，换完先跑"连通性自检"。详见《API密钥与配置更换指南.md》。
2. **要改讲解风格**：只动 `server/services/guide.js` 里的生成 Prompt，硬性约束（只基于资料作答）不要动。
3. **要换语音**：Web 阶段动 `server/services/tts.js`（Edge 音色/韵律）与 `web/scripts/speech.js`（provider 逻辑）；App 阶段新增云 TTS provider，见 15.2。**打包 App 前务必通读 15.2 与打包 Checklist。**
