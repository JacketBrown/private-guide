# 私人 AI 导游 App — 需求确认文档

> 版本：v1.0（需求确认阶段）
> 日期：2026-10-09
> 状态：**需求已确认，尚未开始开发**（等待用户指令）

---

## 一、一句话定义

一个"边走边听"的私人 AI 导游：用户到景点后**拍一张照片**，App 识别出这是哪里，**经用户确认**后，用像导游一样的语气讲出这里的历史故事，并且**每段讲解都可溯源、确保真实性**。

---

## 二、核心使用闭环

```
打开 App
   ↓
[首页] 大而美的拍照按钮（唯一主入口，无列表无地图）
   ↓
拍照 / 从相册选择
   ↓
[识别中] 视觉模型识别（约 1-3 秒）
   ↓
[确认弹层] "我认出来这是「太和殿」，对吗？"
   ├─ 对   → 进入讲解
   └─ 不对 → 用户手动输入文字描述 → 重新识别 → 进入讲解
   ↓
[讲解页] 语音播报 + 文字同步高亮 + 来源标注
   ├─ 播放 / 暂停 / 进度
   ├─ 继续探索：推荐附近可讲点位
   └─ 再拍一张：直接进入下一次识别
```

## 三、已确认的需求决策（逐条）

| # | 维度 | 决策 | 备注 |
|---|---|---|---|
| 1 | 内容来源 | **AI 实时生成** | 不做人工内容库，避开重资产内容制作 |
| 2 | 真实性保障 | **轻标注** | 正文下一行来源小字；底层严格约束"只基于可信资料作答" |
| 3 | 讲解粒度 | **点位级** | 具体到某座殿、某棵树，而非"故宫"这种大景点级 |
| 4 | 主入口 | **拍照** | 唯一主入口，UI 美观 + 实用并重 |
| 5 | 识别交互 | **识别 + 用户确认两步走** | App 先给出识别结果，用户确认或修正 |
| 6 | 兜底机制 | **用户手动输入文字描述** | 识别失败/不准时，用户描述"这是乾清宫前的铜龟" |
| 7 | 下一步引导 | **推荐附近可讲点位** | 讲完太和殿 → "往前走 30 米，中和殿也值得一听" |
| 8 | 讲解长度 | **标准版** | 约 2-3 分钟 / 500-800 字 |
| 9 | 讲解风格 | **混合（D）** | 知识型骨架保真实 + 说书人式开场/彩蛋提味 |
| 10 | 语音播报 | **先系统 TTS，后换大厂音色（D）** | 原型用 Web Speech API；App 阶段换火山/讯飞/Azure |
| 11 | API 接入 | **全真实（A）** | 真识别 + 真生成，可直接带去景区实测 |
| 12 | 产品形态 | **先 Web H5 原型 → 后打包 App** | 先定交互和视觉，再套壳/重写为原生 App |

## 四、技术方案

### 4.1 API 底座（已实测通过）

- **服务商**：TaoToken 中转（`api.taotoken.net`）
- **密钥**：已提供，存放于**本地配置文件**，不进前端代码、不进版本库
- **可用入口**：**按量付费** `https://api.taotoken.net/v1`（实测可用）
  - ❌ Token Plan 入口：返回 `insufficient_quota`，无该模型额度
- **实测通过模型**：`glm-5.3-flash`（视觉+文本，返回正常）

**选用模型**：
| 用途 | 模型 | 理由 |
|---|---|---|
| 拍照识别 | `glm-5.3-flash` | 支持 image_url，快且便宜 |
| 讲解生成 | `deepseek-v4-pro` / `qwen3.7-max` | 文本能力强，适合长文叙事 |
| 备选视觉 | `Kimi-K3` / `qwen3.8-27b` | 均支持 image_url |

### 4.2 真实性保障三层机制

1. **生成时约束**：只喂可信资料（维基百科、景区官方、地方志等公开权威源），要求 AI **只基于给定资料作答**，资料没写的就明说不知道。
2. **溯源托底**：讲解所需的背景资料**实时联网拉取真实公开网页**，作为来源依据 —— 真实性不靠 AI 自觉，而是**每段讲解都有真实资料托底**。
3. **冲突降级**：年代/人物/事件有争议时，正文轻描淡写一句"另有一说……"，不展开、不单列标签（因用户选择轻标注）。

### 4.3 密钥安全

- 原型阶段：前端不直连 API，通过**本地小服务（Node/Python）中转**调用，密钥只存在服务端配置。
- 打包 App 阶段：密钥需放到服务端，或改用账号体系代理调用。

### 4.4 语音链路

```
原型阶段：生成讲解文本 → Web Speech API 播报（锁屏会停，Web 固有限制）
App 阶段：生成讲解文本 → 云端 TTS（火山/讯飞/Azure）→ 原生后台播放
```

## 五、原型页面清单（Web H5，约 4-5 屏）

| 页面 | 内容 |
|---|---|
| 1. 首页 | 大拍照按钮（取景框形态）+ 氛围背景（当季风景渐变/模糊）+ 底部示例引导卡（"试试对着太和殿拍照"） |
| 2. 识别确认层 | 弹层："我认出来这是「太和殿」，对吗？" + 确认/修正按钮 + 手动输入框 |
| 3. 讲解页 | 语音播放器（播放/暂停/进度）+ 文字同步高亮 + 正文下一行来源小字 + 底部"附近可讲点位"推荐 + "再拍一张"入口 |
| 4. 探索/历史页（可选） | 我拍过的点位记录、听过的讲解 |
| 5. 设置页（可选） | 音色试听、讲解长度档位等 |

## 六、UI 设计要求（用户明确关注点）

- **美观**：不能是廉价的"一个圆形按钮"，要有氛围感和品质感
- **实用**：站在人堆里拍照不尴尬 → 支持**相册导入**；拍歪了 → **裁剪提示**；不知道能识什么 → **示例卡引导**
- **减少往返**：讲解页底部直接给"继续探索"，避免每次回首页

---

## 七、待验证/风险点（开发时需留意）

1. **视觉识别准确率**：通用模型认建筑细分（太和殿 vs 保和殿）可能不准 → 靠"用户确认"兜底。
2. **来源资料获取**：维基/百科质量参差，权威资料（地方志、文保单位）常无公开 API → 原型阶段先用公开网页源。
3. **Web 后台播放限制**：浏览器锁屏停止播报，原型阶段无法解决，App 阶段用原生解决。
4. **识别延迟**：现场联网生成有 3-15 秒等待 → 可考虑"进景区预生成缓存"，但原型阶段先不做。
5. **密钥成本**：按量付费，真实调用会产生费用，测试时注意控制。
